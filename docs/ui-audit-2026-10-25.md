# AI Spend Planner UI audit and redesign proposal

The application has useful underlying capabilities, but the current preview is not ready for an unassisted FP&A walkthrough. It exposes forecasting internals before the financial answer, presents conflicting amounts and periods, and can interpret an allocation request as the opposite financial action. Those correctness problems should be fixed before visual polish or additional graphs.

The recommended direction is a streamlined finance dashboard with a contextual assistant. The first layer must be high-level, immediately understandable and easy to use for a nontechnical FP&A manager. It should summarize spending, budget position and the few things needing attention. Users can choose to explore explanations, sources and calculations in greater depth. Keep the existing numerical and approval controls behind that simple experience.

This is an audit and proposed design, not an approved implementation. No application code was changed.

## Core design requirement

**High-level first, depth on demand.** This is an explicit user requirement, not an optional visual preference. Abstraction should turn detailed records into clear financial answers while preserving access to the underlying evidence. The user should not need to understand forecasting machinery to navigate, compare teams or make a reviewed decision.

| Layer | What the user sees | When it appears |
|---|---|---|
| Summary | Key amounts, one primary chart, three to five prioritized issues and a clear next action | Default view; sufficient for routine monitoring |
| Explanation | A selected issue's business meaning, affected teams, dates and financial impact; concise supporting comparisons | On selecting an issue, team, day or “Why?” |
| Evidence and calculations | Original documents, assumptions, coverage, exact values, versions, methodology and technical identifiers | On an explicit request for sources or calculation details |

Keep each layer streamlined. Group related facts into one issue rather than showing every source as a separate alert. Give the user one obvious primary next step and reveal advanced filters, alternative charts and editing options only when relevant. The proposed calendar, breakdowns and scenario tools should be easy to reach; they should not all become additional panels on the landing screen.

Use familiar finance language and short summaries. Carry the selected company/team, period, metric and forecast identity through every drill-down, and return to the same context when it closes. A concise warning that materially changes a decision stays visible beside its value; detailed diagnostics belong deeper. Simplification must preserve financial meaning and traceability.

## Assessment from an FP&A manager's perspective

An analyst should be able to answer five questions without understanding the implementation:

1. What have we spent during the selected period, and how reliable is that amount?
2. Where are we likely to finish relative to a matching budget?
3. Which teams or activities need attention, and why?
4. What would change if a plan, date, or allocation changed?
5. What was approved, by whom, and has it actually been saved?

The current interface can supply pieces of these answers, but requires the user to reconcile different screens and terminology. The most damaging friction is uncertainty about what the numbers mean, rather than the number of clicks alone.

## Findings that should block a polished demo

### 1. Period mismatch makes the over-budget story unreliable

**Priority P1 · Browser and executed.** The header says “Week of Oct 19.” Allocations total $206,000. The dashboard uses an outlook of $2,565,061.03 spanning October 19–December 31, then compares it with those weekly allocations. Research shows $33,000 allocated against $601,040 projected. Every team is labeled over allocation.

This comes from the weekly generated company being combined with a synthetic forecast fixed to October 24 and January 1. The store replaces legacy weekly projections with quarter-view adapters. Status labels do not reject incompatible periods. The original available weekly projections sum to $193,059, which tells a very different story; that sum is not a complete company forecast where scopes are unavailable.

**Required change:** one explicit comparison target must include scope, period, currency, financial basis, dataset and forecast identity. Budget comparisons only appear for matching targets. If no matching budget exists, show “No budget set for this period,” not an over-budget status. Use one demo clock and coherent dated fixtures.

Sources: [generator](../frontend/src/fixtures/generate.ts), [mock forecast](../frontend/src/lib/data/mock-forecast.ts), [store](../frontend/src/lib/store.ts), [forecast adapter](../frontend/src/components/dashboard/forecast-derive.ts). [Browser evidence](../.coordination/ui-audit-20261025/screenshots/04-teams-desktop.png).

### 2. The mock spending headline counts informational usage as spending

**Priority P1 · Browser and executed.** “Total spend to date” is $203,720, while the cost component panel says billable spend is $158,275. The $45,445 difference is included usage, explicitly described as covered by subscriptions and not billed again.

The native backend correctly keeps this distinction. The mock generator gives included usage a positive amount, and frontend totals sum it with charges. Reusing those amounts in forecast illustrations extends the inconsistency.

**Required change:** share one financial aggregation rule across fixtures, KPI cards, charts, team views, proposals and exports. Separate reported charges, estimates and informational included usage. Do not label a total “actual billed cost” if it includes estimated charges.

Sources: [cost components](../frontend/src/components/dashboard/cost-components.tsx), [dashboard aggregation](../frontend/src/components/dashboard/derive.ts), [native ledger](../backend/app/services/spending.py).

### 3. Assistant intent can reverse the user's instruction

**Priority P1 · Browser and executed.** Clicking “Redistribute the existing allocation without adding funding” produced a proposal adding $25,000, raising the envelope from $206,000 to $231,000.

Isolated mock checks also found that “Move $5,000 from Product to Research” becomes added funding; “Add $50” becomes $50,000; and a negative amount becomes positive. The backend parser handles several of these better, but can still interpret a question containing “add” as an action. Changing only the suggestion wording will not fix the underlying interpretation.

**Required change:** explicit action kinds, exact amount parsing, negation/question handling, retained source/destination constraints, and shared semantic examples for mock/backend behavior. Present the resolved action in a short editable card before preview or approval. Missing information must prompt a specific clarification rather than silently selecting funding.

Sources: [assistant suggestions](../frontend/src/components/assistant/assistant-drawer.tsx), [mock intent](../frontend/src/fixtures/generate.ts), [backend intent](../backend/app/compat/intent.py). [Browser evidence](../.coordination/ui-audit-20261025/screenshots/10-redistribute-adds-funding.png).

### 4. A successful save can be reported as “not applied”

**Priority P1 · Executed store reproduction and code.** Applying a proposal waits for the mutation and then separately refreshes budgets. If the mutation succeeds but refresh fails, the combined action rejects. The dialog can claim allocations are unchanged, or remain stuck pending if its retry fails too.

**Required change:** treat the authoritative mutation receipt separately from refreshing the view. Show “Saved; totals could not refresh” after confirmed success. When the outcome itself is unknown, reconcile the stable request/receipt identity before making a claim or retrying. Preserve idempotency and stale-proposal checks.

Sources: [store](../frontend/src/lib/store.ts), [proposal review](../frontend/src/components/allocation/proposal-review.tsx). The browser happy path succeeded; this failure was reproduced in isolation, not by interrupting a live backend.

### 5. The assistant and dashboard disagree about the forecast

**Priority P1/P2 · Browser, executed and code.** The welcome names Security, Sales Engineering and Customer Support as over budget; the dashboard marks all eight teams over. Even the legacy fixture's own identity-matched calculation gives a different list. The greeting indexes reversed forecasts against original-order budgets. Proposal review uses legacy weekly values, such as Research around $47K, while the team page shows around $601K.

**Required change:** join by stable identity and use the same explicit scope, period and issued result for the chart, explanation and proposal's reviewed snapshot. Different snapshots may be shown, but must be named and compared deliberately.

### 6. The primary dashboard is a technical report before it is a finance workspace

**Priority P1 · Browser.** At 1440 × 1000, the initial forecast panel is 4,417 pixels tall. The actual company summary begins at y=4,522; the whole page is 6,236 pixels. Evidence repeats the forecast block before its own filters, which begin around y=4,690. The unfiltered Evidence page is about 20,226 pixels tall.

Team/person pages repeat much of the same machinery. Research's daily chart begins around y=4,792, with People below y=5,315. This makes basic navigation feel like searching a document.

**Required change:** extract the useful parts of the forecast panel into summary, chart, ranked changes, and calculation-detail components. Do not embed the full publication report on every page. Evidence should open directly into search/filtering and summarized changes.

Sources: [Overview composition](<../frontend/src/app/(app)/overview/page.tsx>), [forecast panel](../frontend/src/components/forecast/forecast-panel.tsx), [Evidence composition](../frontend/src/components/evidence/evidence-page.tsx). [Desktop first screen](../.coordination/ui-audit-20261025/screenshots/02-overview-desktop.png).

### 7. Chart legibility has a concrete regression

**Priority P1 · Browser.** The cumulative forecast uses the default white Recharts tooltip with near-white series text. Clicking the line reproduces an almost unreadable value popup. The axis labels use small default dark-gray text on a dark card. Other charts already use a custom dark tooltip, so a working style exists to reuse.

**Required change:** shared chart colors, tooltip, currency/date formatting, readable ticks and keyboard/touch value inspection. Use compact axes such as `$250K`, not `250000`. Do not conclude that the whole dark palette fails contrast: source calculations suggest the normal muted text is materially better than the default chart ticks.

![The forecast tooltip has almost white text on a white background](../.coordination/ui-audit-20261025/screenshots/03-forecast-chart-tooltip.png)

### 8. Actual token data is lost on the real frontend transport

**Priority P1 for the proposed calendar · Code.** The native ledger retains token categories and models, but the frontend compatibility mapping drops unpriced usage, groups away model identity, and emits neither model nor tokens. The rich mock model table therefore does not establish that the real connected interface can display token histories.

The native ledger defines total tokens as input plus output; cached input and reasoning are subsets. Adding all four would double count. The mock currently derives token counts from dollars and fictional prices while its footer says they come from provider exports.

**Required change:** preserve observed usage through a typed daily aggregate API or repaired adapter before building the calendar. Retain unpriced usage, source coverage, model/provider identity, and cost basis. Never derive “actual tokens” from dollars or a forecast.

Sources: [compatibility mapper](../backend/app/compat/mappers.py), [native spending service](../backend/app/services/spending.py), [model table](../frontend/src/components/dashboard/model-breakdown.tsx).

## Recommended product structure

Three approaches are viable. A copy-only cleanup is quick but leaves the financial contradictions and data gaps. A chat-first redesign reduces page density but makes scanning/comparison slower and depends heavily on conversation reliability. The recommended approach is to reorganize the existing dashboard around finance tasks, keeping the assistant contextual and the source trail available.

### Overview

The first desktop viewport should contain a company/period control, compact data status, four summary values, and the main chart. Summary values: **Spent to date**, **Expected period end**, **Budget**, **Expected over/under**. Comparisons are shown only when periods and financial bases match. The token view replaces financial KPIs with observed token totals and coverage; it does not relabel the budget as tokens.

The main chart coordinates actual spending, issued forecast and a matching budget. Actuals use a solid line; forecast a dashed line; supported ranges a shaded band. Mark the latest complete actual day and forecast issue boundary. Latest actual corrections update the actual layer without silently moving a previously issued forecast. If the budget is a period-end ceiling, show it as such; do not invent a daily budget trajectory.

Below it, show a single **What needs attention** summary with three to five grouped issues and clear links to their explanations. Make **What changed** and **Usage activity** easy to open as focused views or disclosures rather than adding every chart and table to the landing page. Default to a company total; make team comparison optional or use small multiples. Eight simultaneous team lines should not be the default answer to “How are we doing?”

### Teams and people

Teams should default to actionable ordering: largest comparable projected overrun, then largest recent spending increase. Add search and sort by spend, variance, forecast and data status. Use compact bars/bullets against matching budget plus a trend sparkline. Each row should include the top relevant change, not just “Likely over.”

A team page reuses the summary/chart at that scope, then shows its top drivers and people. A person page emphasizes observed usage, models/tools, timing and relevant planned work; it must not imply a personal budget exists if none is assigned. Shared/unassigned cost remains explicit.

### Evidence

Remove the repeated company forecast panel. Start with grouped changes and immediately accessible filters. Group multiple source messages into a business event: a launch delay, staffing change, model migration, or price change. Show business summary, affected teams, effective dates, whether it is included in the selected forecast, and source count. Inspecting one event opens the current useful source drawer.

Search/filtering and grouping are separate from numerical effect ranking. A confident statement is not automatically a measured financial effect. Superseded or conflicting plans remain available in details, with the current plan identified clearly.

### Decisions

Keep the explicit review and receipt. Add status, team and period filters; link revisions as versions of one proposal. Show exact before/after amounts, envelope change, reviewed forecast period and approval identity. An applied change should never disappear because refreshing another panel failed.

## Two different explanations of high spend

The proposed high-level popup should answer two distinct questions with two tabs or clearly separate sections. Its initial view contains a short business summary and up to five grouped items; exact calculations and the full source trail open only when an item is selected.

**Where the money went** ranks actual cost contributors within one dimension, such as provider/model, tool, or team. Show dollars, percentage of the eligible total, change from a comparable prior period, and an Other/shared remainder. These values may be summed when they partition the same total. Cost categories, teams and providers overlap; do not mix them into one additive pie.

**What changes the outlook** ranks the largest modeled influences in the selected issued run, scope and horizon. The engine already computes with/without-driver comparisons. Show a short business title, signed financial difference, affected dates, relevant teams and a source link. Default to five available influences; offer See all. Queued or context-only evidence appears separately and receives no invented dollar impact.

These model sensitivities are not proven causal effects or realized savings. Individual omission effects can interact and need not sum to total forecast change. A category-level combined effect requires a joint counterfactual calculation; do not add several effects into a waterfall and call the result explained variance.

Clicking a team keeps the same period/run and filters to the affected team. Missing scope must mean unknown applicability, not automatically all teams.

## Actual spend and token activity calendar

A GitHub-style daily calendar is a good addition, paired with a quantitative trend chart. It helps find bursts, weekly patterns and quiet days; exact amounts and variance still belong in a chart, KPI or table.

Open the calendar through a clearly labeled **Usage activity** entry, retaining the current scope and period. Proposed controls: **Spend / Tokens**, company/team/person scope, and date presets plus a date-range picker. Default to 13 weeks when history is available and no date selection has been made; do not fabricate older days. Keep provider/model filters and token-category detail secondary. Dollar mode distinguishes reported charges from estimated cost. Token mode shows recorded input + output with cache/reasoning detail without double counting subsets.

Each cell has a date, intensity based on amount, and a coverage state. Separate **complete zero**, **partial**, **missing**, and **future**. Future days cannot masquerade as actual usage. Use stable numeric legend thresholds when comparing teams. If scales differ, disclose that explicitly.

Pointer, keyboard or touch selection opens a day summary: tokens, reported/estimated dollars, provider/model/tool breakdown, top contributing teams or people, source completeness and last update. Selection synchronizes the trend and breakdown; reset restores the full range. UTC date bucketing remains explicit; do not relabel daily UTC totals as local days without event-level reaggregation.

Use roving keyboard focus, a readable selected-date summary and table alternative rather than hundreds of tab stops or color alone. Small cells need an adequately sized/spaced activation target or equivalent date control.

**Backend prerequisite:** a bounded daily history response across planning periods, including observed tokens, cost by provenance, separate included-notional value, scope, model/provider, expected/received source coverage, revisions and drill-down references. Preserve all native value kinds, including measured and simulated; never drop them or relabel simulated values as reported charges. Current compatibility records do not meet this contract. Native usage records are a starting point, not a complete calendar feed.

## Forecast ranges and unavailable states

Range-rendering code already exists: the forecast panel conditionally renders separate scenario and historical-error Areas. The mock explicitly returns neither. Therefore “implement error bars” contains three different jobs:

1. Demonstrate a coherent synthetic scenario with supplied, clearly labeled assumptions and bounds.
2. Display the real engine's ranges correctly at the selected scope/horizon, with useful legends and readable chart styling.
3. Connect sufficient compatible observed outcomes before claiming empirically supported historical-error intervals.

Do not manufacture a ±10% band or call scenario bounds “95% confidence.” Daily, weekly and cumulative intervals must come from their appropriate backend targets, not by adding marginal widths. Historical bands are pointwise intervals, not a guarantee that the whole trajectory stays inside the band. A partial scenario range can still omit sources of uncertainty; keep that material qualification accessible next to the selection.

Preserve independent states for value availability, data completeness and range availability. A usable point forecast may lack a historical-error interval. Missing fixed or late charges can leave the total incomplete even when a plotted component is known.

The primary UI should show one short state with an action: **Some costs missing — view sources**, **Range not ready — why**, or **No forecast yet — update forecast**, as appropriate. Unsupported options should not dominate the page with repeated Unavailable cells. A supported daily view should remain available even if the longer outlook is incomplete.

## Assistant and calendar-based changes

Keep one assistant, with a human-readable scope chip such as **Research · October** and an optional selected plan/proposal chip. Starter prompts should map to explicit actions: **Explain a change**, **Try a scenario**, **Adjust budgets**. A question should not accidentally become an allocation instruction.

For “Move the project start to November 10,” resolve the relevant project or ask the user to choose a named plan. Show an editable card with current/proposed start date, end date if relevant, team and supported workload assumptions. Provide both natural-language entry and a calendar popover. Restate relative dates as concrete dates and preserve valid start/end ordering. A date picker used to view history must be visibly separate from one changing a hypothetical assumption.

Make an **Upcoming changes** calendar/list available from a relevant issue, team or planning action for effective plan dates: project starts, staffing changes, model migrations and price changes. Selecting an event opens its sources and scenario edit card. Keep approved/source-backed plans visually distinct from draft what-ifs. This planning calendar complements the historical usage heatmap and opens on demand; it is not another permanent Overview panel. Moving an event must create a preview, not silently rewrite a source document or published forecast.

**Preview impact** should show baseline versus scenario, affected teams/dates, and available uncertainty. The original issued forecast stays intact. “Make it two weeks later” edits that draft rather than creating an unrelated proposal. The existing scenario API replaces the entire driver list, so the client/server adapter must preserve unrelated drivers when applying a local edit.

For “Move $5,000 from Product to Research,” show source, destination, exact amount and **Company budget change: $0**. Editable allocation rows must preserve conservation rules. A scenario changes an assumption; an allocation changes an internal budget. Neither changes observed usage, purchases compute or enforces provider limits.

Approval remains an explicit finance action. Droid can explain, compare, draft and request a refresh, but has no approval tool. Do not add Send for approval or an Undo button that implies an unimplemented workflow. A future reversal of an applied allocation should be a new audited proposal, not deletion of the old receipt.

Answers should use one short summary, one relevant chart or action card, and one clear suggested next step. Reveal optional fields and supporting sources when the user asks for them or needs to resolve ambiguity. Put tool activity and full citations behind details. Show the user's sent message immediately, preserve a newer composer draft on failure, and link progress to real jobs/events. Safe message retries require backend deduplication/reconciliation as well as a stable client message identity; a retry button alone must not create another run or proposal.

| 7 | Representative connected demo and user validation | Coherent engine-backed fixture, browser checks, failure cases and nontechnical task testing |

Phases 3 and 4 can proceed in parallel after the shared semantics/contracts are settled. Do not hide P1 failures behind improved wording. Live Droid remains a separate verification gate; scripted preview success is insufficient.

Proposed usability acceptance targets, to validate with people rather than treat as measured results: find spend/budget position within 30 seconds without opening details, identify two relevant drivers within 60 seconds, inspect a daily token spike within 60 seconds, and revise/preview a dated scenario within two minutes. Users should be able to move from summary to explanation to source and back without losing context. The default page should not require technical vocabulary, scanning source lists or expanding advanced controls to answer routine questions. Run the tasks with several nontechnical finance users, record mistakes and requests for explanation, and revise the targets if real workflows show different needs.

## Reference patterns worth borrowing

- [Claude analytics chat](https://support.claude.com/en/articles/14729354-use-analytics-chat-to-ask-claude-about-usage): compact visual answers, contextual follow-ups and visible data freshness.
- [Claude Console usage and cost reporting](https://support.claude.com/en/articles/9534590-cost-and-usage-reporting-in-the-claude-console): separate consumption from financial cost and provide model/time filtering.
- [Codex review](https://learn.chatgpt.com/docs/code-review?surface=app): make proposed changes inspectable at the right scope before application. Adapt this to financial cards without pretending applied decisions can simply be erased.
- [GitHub contribution calendar](https://docs.github.com/en/account-and-profile/how-tos/contribution-settings/viewing-contributions-on-your-profile): daily selection and range exploration connected to detail.
- [W3C keyboard guidance](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html), [color guidance](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html), and [chart alternatives](https://www.w3.org/WAI/tutorials/images/complex/): access to the same information without pointer hover or color perception alone.

These are documented patterns, not claims that Claude or Codex currently offers a native token heatmap. The proposed calendar is a GitHub-inspired adaptation for this product.
