# Search, synthesis and evidence method

Research date: 2026-10-24. The user requested a new investigation from scratch with at least twenty agents in parallel, replacing the prior dossier. Twenty workers were simultaneously running, each assigned a distinct substantive track with fresh conversation context. The previous dossier was archived for recovery and excluded from their analytical inputs. The original transcripts and master/workstream plans supplied requirements; prior numerical choices embedded in the forecasting outline were treated as provisional and reassessed.

## Search scope

The searches covered financial definitions/standards, provider/cloud/coding-tool reports, telemetry and public traces, staffing/project data, classical/structural models, intermittent/compound demand, pooling, reconciliation, tabular ML, task-trained neural models, current foundation models, contextual forecasting, change detection/adaptation, uncertainty, agent sessions, evaluation/selection, decision utility, operations and adversarial workflow failures.

Workers used web search and direct source retrieval, favoring original papers, author manuscripts, standards, provider documentation, official code, release metadata and model/dataset cards. Search terms were adapted within each track rather than fixed into a formal systematic-review protocol. This is a broad architecture review, not a PRISMA-style exhaustive systematic review. Sources were retained for direct capability/mechanism/comparison evidence, important counterevidence or deployment constraints; generic commentary and leaderboard rank alone were not architecture evidence.

Records preserve source title, URL, author/organization, publication/version when verified, access date, source kind, supported claim, applicability limits and license status. Current source and checkpoint versions were examined because older family descriptions can be materially wrong. Some papers were available only through author abstracts or official indexed content; those limits remain in the records. No paper's license was assumed to authorize its dataset or model weights. Mutable pages are dated but not all are archived byte-for-byte; future implementation must pin dependencies/checkpoints and re-check deployment terms.

## Synthesis process

Each worker wrote an independent analysis, structured source registry and domain faults before integration. Root selected a common target/identity/time vocabulary, compared contradictory findings and wrote the architecture and experiment sequence. Cross-review paired financial targets with connectors, telemetry with sessions, pooling with model families, reconciliation with probability semantics, enterprise context with operations, uncertainty with contextual/foundation/adaptation claims, evaluation with decision selection, and requirements with architecture.

Material corrections included compound-sum variance assumptions, nonlinear recursive means, quantile-to-mean limitations, interval/probability capability separation, complete-period contract state, source gates appropriate to each target, field-level delayed prefix data, and training-label maturity. Cross-review is reasoning evidence, not executed model validation. Final document/JSON/link/provenance checks are recorded separately.

## How to interpret the output

Established evidence is a source-supported fact, mathematical result or original requirement; its domain/assumptions remain attached. Inference applies that evidence to this product. Proposed design is a chosen interface, comparison or response not yet implemented. Unvalidated hypothesis is an empirical relationship to test. Synthetic examples are arithmetic or fault specifications and carry no real-world prevalence claim.

A winning architecture cannot be identified solely by counting supportive sources. The recommended modular architecture preserves falsifiable alternatives and defines the experiments that choose a useful configuration. No model training, enterprise data download, authenticated billing test, performance benchmark or causal savings study was conducted in the research phase. Completeness means an implementer can identify what to model, ingest, compare, test and refuse; it does not mean all unknown enterprise facts have been resolved.
