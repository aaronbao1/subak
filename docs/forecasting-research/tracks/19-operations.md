# 19 — Operational architecture, reproducibility, isolation, and deployment gates

Research date: 2026-10-24. This track proposes contracts and acceptance tests; no application behavior, operational benchmark, or forecasting experiment was executed. It independently uses the master plan, backend/Factory/frontend plans and original discussion transcripts. The master plan settles ownership and internal-budget scope; transcript enthusiasm about firm-wide context does not establish permission to expose every source to every user. Individual modeling remains a possible backend granularity, not a personal UI commitment.

## Established evidence

The project explicitly requires repeat imports not to double spending; cumulative counters not to become independent events; delayed/missing forecasts not to disable observed-spend access; stale budget proposals to receive renewed review; and changes to persist exactly once with finance approval. Backend owns facts, authorization, arithmetic and persistence; forecasting owns numerical projections; Factory owns semantic interpretation and assistance; frontend owns interaction. These are requirements, not conclusions from vendor documentation. See [master plan](../../ai-spend-master-plan.md), [backend plan](../../backend-plan.md), [Factory plan](../../factory-agent-plan.md), and [frontend plan](../../frontend-plan.md). Relative plan links target the final `docs/forecasting-research/tracks/` destination.

Important primary-system evidence:

- Feast's current point-in-time documentation explicitly says default joins constrain event time, while created timestamps otherwise resolve duplicates. Consequently, late corrections can enter old feature rows. Its optional `filter_by_created_timestamp=True` adds the availability constraint, excludes NULL created timestamps, and is not supported by every offline store. This is direct evidence that a feature store's “point-in-time” label alone does not establish historical availability correctness. The actual installed release/backend must be tested. [Feast PIT joins, live documentation](https://docs.feast.dev/getting-started/concepts/point-in-time-joins).
- Apache Iceberg represents table state using immutable files, snapshot metadata and atomic pointer replacement. Readers keep the loaded snapshot; conflicting writers must validate/retry. This supports the snapshot-publication pattern, not a requirement to adopt a lakehouse or proof of atomicity across several independent tables. Live spec navigation identifies 1.12.0 and includes newer format material; compatibility requires pinning actual format/engine versions. [Iceberg specification](https://iceberg.apache.org/spec/).
- PostgreSQL 18 provides exact `numeric`, but declared scale can round input. `timestamp with time zone` normalizes to UTC and does not retain the original zone; bare `timestamp` lacks zone semantics. Row security has owner/superuser/BYPASSRLS exceptions. Serializable transactions prevent serialization anomalies, but applications must handle retries. These are useful reference semantics, not a prescribed database. [Numeric](https://www.postgresql.org/docs/18/datatype-numeric.html), [date/time](https://www.postgresql.org/docs/18/datatype-datetime.html), [row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), [isolation](https://www.postgresql.org/docs/18/transaction-iso.html).
- Amazon's idempotency guidance uses caller request IDs and atomic recording of token plus mutation, distinguishes late retries, and rejects a reused token with different intent. A deduplication cache separate from the budget transaction cannot provide the same guarantee. [Amazon Builders' Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/).
- MLflow registry distinguishes numbered model versions from mutable aliases. Its documentation describes lineage and deployment tags but does not make an alias an immutable run identity or automatically preserve all external input bytes. [MLflow registry, current docs](https://mlflow.org/docs/latest/ml/model-registry/).
- OWASP describes indirect prompt injection through retrieved files and influence over decisions/tools; retrieval augmentation does not eliminate it. Breck et al.'s 2017 ML Test Score identifies 28 production tests/monitoring needs, illustrating that model accuracy alone does not establish deployability. Neither source establishes this product's security or performance. [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/), [ML Test Score](https://research.google/pubs/the-ml-test-score-a-rubric-for-ml-production-readiness-and-technical-debt-reduction/).

## Inference: begin with strong boundaries and few deployment units

A small finance product with daily/periodic forecasting can plausibly use one transactional backend, retained raw objects, a versioned forecasting package and background jobs. This reduces service credentials, queues, distributed transactions and operational work. Separate modules and explicit contracts are valuable immediately; four owners do not imply four network services. Forecast/context jobs should run with bounded resources away from the interactive request path when a timeout or memory spike could otherwise take down spending/budget access.

This is conditional on measured workload. Independent scaling, incompatible runtimes, slow training, noisy tenants, GPU needs, or separate deployment/security ownership could justify a worker service. A large lakehouse, online feature store and external registry are not initial correctness prerequisites. Conversely, a single-process prototype with mutable CSVs and no provenance does not satisfy the requirements merely because it is simple.

## Proposed design: evidence ledger and snapshot contracts

**Separate facts from projections.** Preserve source payloads by immutable object generation and checksum; normalize observations into versioned records. “Immutable” means ordinary corrections append revisions; it does not prohibit authorized retention/deletion workflows. Keep distinct ledgers for observed usage/charges, contextual evidence/signals, forecasts, and finance decisions. Forecasts never rewrite measured charges, and proposals never count as decisions.

Every normalized observation needs tenant/source-account identity, connector/parser version, source record or generation identity, quantity kind, value, unit/currency, financial basis, coverage scope, service interval, source revision/publication timestamps when supplied, receipt/availability timestamps, requested/returned field manifests, and supersession/reversal links where meaningful. Absent fields can be unknown, not requested, or permission-limited; preserve that reason rather than treating all as ordinary missing values. Retain original source precision. Token usage, local estimated cost, reported charge, included entitlement and fixed fee are not one universally summable measure. Explicit category/overlap rules must prevent counting estimated usage costs beside their replacement invoice charge. Source authority is conditional on target, scope and completeness; “newest wins” is not sufficient. See connector track 03 for export replacement semantics and financial track 02 for target definitions.

**Bitemporal meaning.** `effective_start/end` answers when usage, price, membership or a plan applies; `available_at` answers when this system could consume that version. Store source publication separately: a plan dated Monday uploaded Friday was not available to this system Tuesday. If researching what the organization could have known instead, define and evidence that different cutoff explicitly. Derived feature/signal availability must include upstream processing completion (`ready_at`), not merely receipt of the original source; an unfinished extraction was not yet consumable. Do not backdate availability during historical imports. Supersession history permits both “latest corrected view” and “what this run knew” queries. Where genuine historical availability is absent, label the replay retrospective rather than operationally faithful.

A manifest must bind the *whole read*: tenant, forecast origin, financial/calendar basis, source generations and coverage intervals, observation revision set, mapping/price/FX versions, context versions, permissions classification, transform version and checksums. Write staged objects, validate counts/control totals/coverage, then atomically activate one manifest reference. A crash before activation leaves the former complete snapshot available; missing a replacement-export part must not create a partial new period. Relational transactions can implement this for small data; object-store listings alone cannot establish a coherent multi-table snapshot. Never require every connector to share append/upsert semantics.

For time, retain UTC instants plus the original source zone/offset where supplied, report-calendar zone and explicit half-open period boundaries. Calendar month remainder is not “30 days,” nor is a local calendar day always 24 elapsed hours. Preserve date-only precision as date-only; reject or quarantine ambiguous local instants instead of inventing offsets. Decimal amounts or explicitly scaled integer units belong at financial boundaries; model computations may use floats, with finite-value checks and deterministic rounding only at the specified boundary. Sub-cent API costs must survive aggregation; do not round every request to cents. Keep currencies and internal-credit units distinct unless a versioned conversion is explicitly authorized.

## Proposed design: reproducible forecast and model contracts

| Contract | Minimum content and invariant |
|---|---|
| Target | Version, quantity/currency, financial basis, population, interval/calendar, disjoint cost components, aggregation operator, truth-maturation/revision policy and exclusions. A model emitting tokens cannot satisfy a USD target. |
| Features | Definition/version, source lineage, event and availability cutoffs, missing-versus-zero semantics, timezone, mapping version, transformation/environment identity. Learned transforms fit only permitted training data. |
| Context signals | Source revision and passage, applicable interval, subject/team, event/plan status, supersession/conflict, extraction model/prompt/schema version, extraction uncertainty. Extraction confidence is not an occurrence/spend probability. |
| Run/artifact | Immutable run ID; manifest; target/feature/model/policy versions; code commit, dependency lock/runtime/container; parameters/seeds; training/validation cutoffs; weights/artifact digest; numerical tolerance/determinism limits; diagnostics and evaluation record. |
| Result | Origin, target start/end, as-of snapshot, freshness/coverage, method and artifact identity, point statistic, supported uncertainty with semantics, scenario identity, assumptions, status/reason and fallback lineage. Store actual outputs for later explanation. |

Evaluation/scoring labels may mature after the prediction origin. Labels used in fitting, calibration or model selection must instead be available by that operation's simulated cutoff; revised labels can leak future information too. Record the version used for evaluation truth separately from the version visible at origin. A backtest and an audit replay are different operations. A registry can initially be a database table plus content-addressed files; MLflow becomes useful when collaborative promotion, many runs or serving integration justify operating it. Resolve a mutable champion alias once, record its numbered version/digest, and use that artifact throughout the job. Retain output artifacts even when nondeterministic hardware prevents bit-for-bit reruns; reproducibility claims must state tolerances.

Promotion requires input/target compatibility, measured forecast performance and operational acceptance. Rollback must restore the model *and* compatible feature/target code. Database/schema changes should expand first, test readers of both supported versions, backfill into a new generation, then switch; do not mutate a historical target's semantics in place. A renamed cost category can be a semantic breaking change even if its JSON type stays numeric.

Status should separately expose job state, data completeness and age. A compatible validated baseline may replace a failed model only with an explicit reason and lineage. Otherwise return unavailable. A prior forecast can be displayed as stale with its original origin/target; it must not silently become today's forecast. Failure of one source/tenant/model/context job must not turn other sources into zeros or block authoritative spending and budget reads. Context failure can permit an explicitly context-free forecast only if that model/target has been validated. Partial-team results must not appear as a complete company forecast.

## Proposed design: boundaries, security and finance integrity

Factory retrieves scoped evidence and produces structured interpretations/proposals; it never gets unrestricted database or provider-spend credentials. Forecasting accepts validated signals and owns whether they become features or scenarios. Frontend preserves supplied financial periods and status, and only renders a saved-success receipt from backend confirmation. Budget application accepts actor/tenant, proposal ID/hash, expected budget version and idempotency key; it transactionally validates authorization, current version, unit and transfer/addition arithmetic, saves the mutation/audit receipt and records the key. A retry returns that receipt. Reusing a key with a changed amount fails. Concurrent changes make the old proposal stale; retry logic must not silently rebase finance's decision.

Tenant scope must participate in source keys, jobs, manifest IDs, registry references, cache keys, evidence retrieval and artifact authorization—not only SQL filters. Test with the actual runtime role because owner roles can bypass RLS. Apply historical availability and current authorization as separate predicates: a historically visible record is not permission to disclose it today. Restrict source context before retrieval and recheck evidence access before rendering; a cached cited summary may outlive a document ACL change. Derived signals and models require an explicit access policy; aggregation is not automatically de-identification or permission to share. Prefer needed team-period aggregates and pseudonymous individual keys over raw correspondence or personal attribution. Do not place document bodies, tokens or unbounded prompts in ordinary logs.

Retrieved text is data, including claims that a budget is “approved” or that an invoice should be ignored. Schema validation, citation existence and model confidence do not prove the claim true. Bound document-to-signal transformations, preserve conflict/authority status, prohibit source text from granting tool capability, and require the finance decision path for mutations. Test semantic poisoning as well as obvious “ignore instructions” attacks: a plausible forged plan can alter a forecast without any unauthorized API call. Human review and calibrated signal validation reduce this risk; they do not eliminate deliberate falsification.

Deletion/permission revocation needs lineage traversal through raw objects, embeddings, caches, signals, training extracts and model artifacts. Tombstone inaccessible evidence immediately; invalidate or rebuild dependent artifacts according to the organization's retention/deletion policy. Historical receipts can retain permitted non-sensitive metadata and disclose that evidence was removed. Do not promise full content replay after erasure. Hashes are not automatically anonymous; predictable sensitive content can be guessed. Exact legal retention duties remain jurisdiction/contract dependent and are not determined by this research.

## Alternatives and overturning evidence

| Shape | Best-fit assumptions | Operational tradeoff and disconfirming experiment |
|---|---|---|
| Lean package + jobs | Limited source count, modest team-series count, batch refresh, shared small team | Lowest deployment burden; application owners implement manifests, retries and monitoring. Run representative cold-start and peak-load jobs while finance reads/writes continue. Failed isolation or missed refresh windows overturn the recommendation. |
| Separate forecast/context services | Runtime/GPU isolation, independent scaling or ownership, large jobs | Adds RPC contracts, queues, version skew, tracing, secrets and retry semantics. Demonstrate that independent scaling materially lowers latency/cost or failure blast radius compared with a bounded local worker before splitting further. |
| Managed forecasting platform | Authorized cloud data placement, existing expertise, compatible targets and sufficient budget | Outsources some training/serving operations; retains ingestion, point-in-time correctness, evaluation, ACLs and financial semantics. Measure end-to-end latency, export/replay fidelity, cold series behavior, cost and fallback—not just a vendor accuracy metric. |

Current counterexamples matter: Google AutoML forecasting documentation specifies batch inference and points to a different workflow for online inference. AWS documents Amazon Forecast as closed to new customers since 2024-07-29 and plans no new features. Thus availability, mode, region, artifacts, retention and exit/migration are procurement gates, not interchangeable implementation details. [Google forecasting workflow](https://docs.cloud.google.com/gemini-enterprise-agent-platform/machine-learning/tabular-data/forecasting/overview), [AWS transition notice](https://aws.amazon.com/blogs/machine-learning/transition-your-amazon-forecast-usage-to-amazon-sagemaker-canvas/).

## Proposed acceptance and deployment/cost gates

Before connecting finance actions: execute the ten faults in `edges/19-operations.json`; prove snapshot integrity, exact budget arithmetic, one receipt per action and tenant isolation. Before showing a forecast as decision-grade: verify target compatibility and availability-aware replay; establish coverage/freshness policy and rolling-origin quality/calibration against baselines, including late-bill and cold-team conditions. Synthetic demos can establish plumbing, not accuracy.

Before deployment: pin artifacts/dependencies; rehearse backup restoration, compatible rollback, staged-schema migration, permission revocation/deletion and a worker crash while budget reads/writes remain available. Declare measured p95 request latency, refresh completion deadline, recovery target, queue bound and maximum stale age for the chosen workload. No universal numbers are supplied here: thresholds should be chosen from the finance workflow and tested at expected load plus an agreed margin.

Cost gate: record connector/API calls, storage including retained snapshots, CPU/GPU runtime, training searches, inference, embedding/LLM tokens, egress and operator time per tenant-refresh. Cap retries, concurrent jobs, context size and training trials; coalesce identical snapshot/target requests. Compare measured cost per accepted forecast and incremental decision value with a simple baseline. Stop promoting complexity when improvement fails its prespecified practical threshold or cost cap; a costly model with excellent benchmark ranking can still lose. Current prices and actual quotas require account/region verification before selecting a vendor; no price assumption is treated as evidence.

## Unvalidated hypotheses and remaining uncertainty

A package plus isolated worker will probably suffice for the initial company/team workflow, but neither real history nor tenant scale is supplied. The value of immutable fine-grained retention versus privacy/storage burden depends on actual data and policy. Context-free fallback may be adequate during extraction outages, but only evaluation can establish that. Model quality, refresh cadence, exact stale tolerances and managed-platform economics remain open. The architecture deliberately allows contrary results to change deployment shape or model choice without changing the authority of finance decisions or the meaning of historical facts.
