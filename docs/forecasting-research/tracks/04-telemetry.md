# Usage observation, ancestry, and public traces

Research date: 2026-10-24. Scope: human teams and human-initiated agents; internal finance planning. This note uses fresh primary-source checks and the master/backend/Factory/frontend requirements. It does not inspect private usage in bulk, download public corpora, implement connectors, or claim forecasting accuracy.

## Established evidence

The master plan requires duplicate imports and repeated cumulative telemetry to leave spending unchanged, explicit team mappings, visible incompleteness, and separate measured usage, estimated cost, reported charges, subscriptions, and included usage. The internal transcript motivates individual/task/project granularity beneath team forecasts; the mentor transcript questions whether available historical data represents enterprise complexity. Neither transcript supplies a verified enterprise history. Their supplied October 23 dates and speaker labels remain unchanged; this research does not infer a transcript year.

OpenTelemetry GenAI conventions moved into a separate repository; the old website pages say they are no longer maintained. The current repository has no published schema URL in its README and its changelog is unreleased. Client inference and agent conventions are marked **Development**. Therefore an implementer must record the adapter's exact schema/content version, not assume that the main OTel website version identifies the GenAI contract. The inspected documents reference core semantic conventions v1.44.0; the separately inspected OTel metrics/tracing website identifies OTel 1.62.0. An immutable GenAI commit was not obtained during this review. [Moved documentation](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans/), [GenAI repository](https://github.com/open-telemetry/semantic-conventions-genai), [changelog](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/CHANGELOG.md).

The inspected inference contract defines provider, requested/response model, conversation ID, prompt version, input/output usage and cache/reasoning details. Input includes cache subsets; reasoning belongs inside output. The new cache-write spelling is `gen_ai.usage.cache_write.input_tokens`. The contract distinguishes the instrumentation's provider knowledge from the actual upstream provider behind a proxy. It prefers billed counts when both billed and model-consumed counts exist. This is a convention, not proof that an installed SDK implements it correctly. [Client inference](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md).

The current token-metric design uses monotonic `gen_ai.client.inference.usage.*` counters for consumption, with cache/read/write and reasoning subsets. Per-operation histograms describe distributions and explicitly are not the instrument for total usage/cost. Usage measurements are known positive contributions; an absent metric point does not establish zero activity. [Token metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-token-metrics.md).

Logical GenAI spans can cover automatic retries; agent conventions add stable agent ID/version and agent/workflow/tool operations. Consequently span count is not provider-request count, agent identity is not a run identity, and a tool invocation need not imply another charged model call. [Logical spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md), [agent spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md). OTel supplies trace/span relationships and links, but finance ownership needs its own mapping. [Tracing API](https://opentelemetry.io/docs/specs/otel/trace/api/).

Provider streaming semantics must be adapter-specific. Claude documents cumulative usage in `message_delta`, a final `message_stop`, possible in-stream errors, and future unknown event types. Adding each snapshot would overcount. [Claude streaming](https://platform.claude.com/docs/en/build-with-claude/streaming). At the aggregate metric level, OTel separately supports cumulative and delta temporality, observation/start timestamps, and reset/gap/overlap semantics. A decrease without stream identity and reset evidence is not safely interpretable as a refund or new usage. [Metrics data model](https://opentelemetry.io/docs/specs/otel/metrics/data-model/).

## Inference: choose observability by the decision it supports

An invoice total can support historical charge forecasting but cannot recover active-session continuation. An unsampled request meter can improve freshness, although only reconciliation establishes its relationship to reported charges. Session/tool ancestry can support ongoing-run forecasting but cannot replace a team ownership map or prove that external calls were fully captured. None of the reviewed public traces supplies both enterprise team identities and finance/context history. These are data-boundary conclusions, not model-performance results.

## Proposed design: durable observations before derived totals

Use three related stores: immutable source observations; versioned normalized meters; and derived views selected by an explicit basis and as-of time. Keep reported-charge records in their own fact family. A billing amount and its underlying token estimate describe overlapping economic activity and must never be summed simply because both arrived.

The proposed minimal ingest contract is below. Nullable values carry a reason (`unsupported`, `not_yet_reported`, `redacted`, `unknown`, or `parse_error`); known zero remains numeric zero. Preserve raw provider names and values even when normalized.

| Field group | Required meaning |
|---|---|
| Provenance | tenant, connector/source instance, source object/export ID, source record ID, content hash, raw locator, adapter version, schema version/hash, instrumentation name/version, ingestion batch ID |
| Time | event start/end or explicit source interval, provider/reporting timezone, observation timestamp, source publication timestamp if supplied, first-seen/ingested timestamp, valid-from/revision time, precision, clock-quality flag |
| Identity | logical operation ID, provider request/response ID when exposed, retry attempt ID, trace/span/parent span IDs, links, conversation/session ID, human turn ID, run ID, parent run ID, initiating principal pseudonym, project/workspace/key reference |
| Runtime | harness name/version, agent version, prompt/config hash, tool name/version, requested and response model, provider endpoint and biller, deployment/model revision when known, modality, service tier |
| Meter semantics | metric name, unit, integer/decimal value, source scope (`request`, `turn`, `session`, `process_stream`, `bucket`), `delta`/`cumulative`/`final_total`, counter epoch/start, sequence, subset-of relationship, billed/model-consumed/local-estimate basis |
| Finality and coverage | provisional/final/corrected state, success/error/cancel status, stream completion evidence, sampling policy/probability when known, covered interval, missing partitions, parse failures, authoritative-source rank |
| Ownership and money links | effective-dated team mapping ID and mapping version, unassigned reason, optional charge linkage/reconciliation batch; no inferred universal token-to-dollar conversion |

This is a data-design proposal, not a claim that every connector exposes these fields. Store supported subsets and an explicit capability matrix. Keep prompt/output content outside the minimum meter path; content ingestion for company plans remains a separate authorized corpus. Numeric metadata, tool names and prompt/config hashes can often support the first test without retaining code or prompts.

Use provider request ID plus account/endpoint namespace as a preferred attempt key, while retaining a source-native event key. A content hash deduplicates identical copies, not independent identical requests. A source-native ID is insufficient across tenants, exports, or providers. Cross-source matches require evidence and lineage: a wrapper span, HTTP span, streaming final object and provider usage bucket may overlap without sharing keys. Choose one accepted meter per covered request/category; retain competing observations and their discrepancy.

Ancestry is a graph: a conversation can contain several user turns and runs; a run can contain multiple attempts and tools; asynchronous work can use links rather than a single nested parent. Store one economic attempt once and derive multiple attribution views. Parent summaries are rollups, not new usage. For shared work or missing ancestry, retain unassigned/shared usage rather than duplicating it across parents. The initial user-facing aggregate remains company/team even if pseudonymous individual activity helps model fit.

Normalize provider counters by the declared scope. For a known cumulative epoch, order by source sequence/event time and derive differences between accepted observations. Replaying 100, 150, 150 yields 150 total, not 400. An out-of-order 120 between 100 and 150 changes interval placement without increasing the final 150. A first observation of 500 with unknown start proves a snapshot of 500, not that 500 occurred after monitoring began. A reset starts a new epoch only with source evidence; unexplained negative differences are quarantined. Do not assign an entire session cumulative delta to the latest request unless that request's scope is verified.

For streaming, maintain separate per-field values and source sequences, not a blanket maximum over all payloads. Known final authoritative totals supersede provisional snapshots; corrections can decrease them. An interrupted stream is incomplete, not a zero-cost failure. Counting visible text with a local tokenizer is a separately labeled estimate, not a substitute for hidden reasoning, tool serialization, cache meters, or provider billing units. Unknown events should preserve raw data and mark adapter compatibility rather than silently becoming spend.

Cache/reasoning/modality fields form an inclusion graph, not additive categories. Example: total input 1,000 with cache-read 700 remains 1,000 input; output 200 with reasoning 120 remains 200 output. Price estimation may need disjoint billable buckets derived using verified provider rules. If cache subsets are absent or conflict, do not infer a partition. Preserve the unknown portion and report incomplete price coverage. Tool compute, search, containers, storage and subscriptions require separate unit-bearing records.

Use bitemporal queries for evaluation: records incurred before cutoff but received later are excluded from the original forecast's information set. Revisions update current summaries with history retained; they do not rewrite what finance knew then. Recompute affected aggregates and future forecasts after late arrivals, with lineage to the revision. Coverage has separate collection, attribution, token-meter and price coverage dimensions. A fast connector with no successful partitions is not complete merely because its last poll was recent.

## Alternatives and what could overturn the recommendation

| Telemetry level | Data and useful target | Burden and failure mode | Proposed comparison |
|---|---|---|---|
| Reported provider charges/buckets | Historical dollars by available account/project; later team mapping | Lowest instrumentation burden; delayed/revised data, coarse categories, weak live continuation | Compare charge-only forecast/nowcast to request-enriched forecast on the same as-of snapshots |
| Unsampled request meter plus reconciliation | Request tokens, models, error/retry/cache; estimated variable cost | Moderate integration and mapping burden; duplicate instrumentation, missing streams, hidden upstream requests | Measure reconciled coverage, freshness benefit and forecast loss, not merely more rows |
| Session/run/tool metadata | Above plus ancestry and partial-run state | High-cardinality state and version maintenance; selection bias, censored runs, ambiguous parent rollups | Ablate session features and test calibration of remaining-session usage using only prefix information |
| Content-bearing trajectories | Above plus task semantics | Highest governance/storage cost; transcript leakage, truncated histories, context/harness mismatch | Only adopt if metadata-plus-authorized-context is materially worse on held-out enterprise periods |

Working recommendation: support charge/bucket imports first where that is the accessible source; design the common contract for request and ancestry enrichment, without requiring full content. An organization with trustworthy unsampled request records may reasonably start there. Evidence that aggregate-only methods match accuracy, freshness and finance usefulness at lower operational cost would overturn the preference for richer telemetry.

The Azure [data license](https://github.com/Azure/AzurePublicDataset/blob/master/LICENSE) and BurstGPT [license](https://github.com/HPMLL/BurstGPT/blob/main/LICENSE) explicitly specify Attribution 4.0 International. Nebius is a dataset-card declaration; underlying code provenance/third-party rights were not audited. Preserve attribution, source version and modifications with any redistributed sample.

The Copilot [schema](https://github.com/Azure/AzurePublicDataset/blob/master/analysis/GitHubCopilotCodingAgents/schema.json) supports a useful concrete importer design: session → turns → LLM calls and tool batches; call `message_id`, timestamp, duration, initiator type, model, result/status, token total/prompt/completion/cached/cached percentage; message segment type/role/position/token length; tool-batch request ID links to call message ID; tool status and duration. It does **not** document provider request attempt IDs, separate reasoning tokens, invoices or export-arrival history. Do not invent those columns.

For all public traces, split by time and group related sessions/issues before any task-level randomization. During a continuation test expose only the prefix available at the prediction time; final token counts, eventual cancellation, final patch, future tool statuses and full-session length are labels or future information. Population/model anonymization precludes a dollar forecast unless explicitly imposing hypothetical prices. Do not turn sessions into fictional individuals or teams and report resulting accuracy as enterprise evidence.

## Unvalidated hypotheses and proposed verification

1. Session-prefix growth, retry/tool state, cache behavior and harness version may improve remaining-run prediction beyond elapsed time and accrued tokens. Test grouped prefix backtests on Copilot, then independently on authorized enterprise data; compare calibration and tail loss, not just average error.
2. A metadata-only request ledger may capture most practical finance value. Test against aggregate charges and content-enriched models on identical targets/cutoffs; include maintenance and coverage failures.
3. Cache regime shifts and harness changes may explain spend changes independently of human activity. Model them only after observing stable versions and billing reconciliation; anonymized public model labels cannot identify a real tariff change.
4. Late-arrival nowcasts may matter more than future-run modeling. Public traces lack ingestion vintages, so this requires real connector arrival histories or explicitly synthetic fault scenarios.

The separate edge register gives ten proposed faults. No fault or forecasting experiment was executed in this research phase. Local traces remain feasibility evidence only, as required by the master plan. Completion of this track is documentary verification, not implementation readiness or enterprise validation.
