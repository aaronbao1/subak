# Enterprise usage and billing connectors

Research date: 2026-10-24. This track was rebuilt from currently fetched primary documentation. No customer account or authenticated billing endpoint was queried. Documentation availability, tenant entitlement, successful authorization, available history, and invoice reconciliation are five different facts; only the first is established here.

All cited provider pages were opened and their relevant public text inspected; no matrix claim relies solely on a search snippet. Access limitation: the ChatGPT guide's separate authoritative Admin schema was not inspected, so its detailed endpoint fields, temporal contract and pagination remain unresolved here. Publication dates and reuse licenses remain unverified where the source records say so.

## Established evidence: what can be connected

The master plan and backend plan require one practical authorized source, explicit team mappings, separation of usage/estimates/charges/subscriptions, idempotent imports, and visible incompleteness. The original internal discussion asks how historical token spend is ingested; the mentor discussion challenges representativeness and missing bills. Those requirements favor a bounded financial target with demonstrable coverage over a large connector count. Source IDs below map to the accompanying bibliography.

## Inference: what those capabilities permit

A daily reported-variable-charge target is often feasible before all-in spending is feasible. A source can be authoritative for its own reported charges yet omit commitments, seats, provider marketplaces, taxes or another account. A team breakdown additionally needs a company-approved, effective-dated mapping. An API user can be a service identity; a cloud IAM principal can represent a gateway; a workspace can contain several teams. Public identity fields do not resolve these relationships.

Do not join records merely on model name and timestamp. One Claude call may appear in local coding telemetry, a proxy, a cloud billing export and a tool's activity report. Those are multiple observations of potentially one economic event. Conversely, a tool subscription and independently paid API usage can be two legitimate obligations. Establish payer, contract, billing account and coverage before deciding. An unresolved overlap should block a purported exhaustive total, while retaining the individual source views.

Recent events and historical revisions are separate issues. A feed's usual five-minute arrival does not establish an immutable five-minute close. A backtest constructed from today's revised export can leak future corrections unless earlier source snapshots were retained. Likewise, requesting several months from a paginated endpoint does not prove that all those months exist or are complete.

## Proposed design: first-source decision

Choose by a scored evidence review, not provider brand. The hard gates are authorized retrieval; explicit payer/account/product scope; at least one reproducible subtotal; target-appropriate temporal semantics; documented or inspectable units; and an explainable completeness state. An incurred-spend target requires incurred/service timing; a billed-period target requires billing-period timing; a usage target requires the relevant meter/event interval. If the desired time basis is unsupported, explicitly narrow or switch the target rather than relabel observations or reject a legitimate billed-period/usage source. Then compare retained history, attribution coverage, correction behavior, invoice tie-out, extraction effort, and concentration of the company's actual spending. Record both satisfied gates and unknowns.

1. Prefer an existing authorized export when it has useful history and a known control total. This is the lowest-integration-risk route to honest ingestion and a finance demonstration. It does not prove live connector operation.
2. For a direct-API-heavy company, pair OpenAI Usage+Costs or Anthropic Usage+Cost. These give complementary activity and charge views. Anthropic Priority Tier exclusion and OpenAI conditional historical grouping can change which target is supportable.
3. For a cloud-heavy company, use its existing CUR/Azure/BigQuery billing export first; add telemetry for recent usage and attribution. Cloud exports can cover wider spend but have longer delays, account-specific schemas and more financial categories.
4. For a coding-tool-heavy company, evaluate its billing export/API and subscription contract together. Activity analytics alone cannot define payable spend. Avoid assuming a newly available endpoint supplies a long pre-migration history.

These are conditional preferences, not a universal ranking. A source with 12 months of reconciled daily history and weak person attribution may be better for company forecasting than a detailed user stream available for only one week. Company-level validation can proceed while team forecasts remain unavailable. If no real source passes the hard gates, implement the authorized-file adapter and clearly synthetic fixtures; withhold empirical enterprise-accuracy claims.

## Proposed connector contract

Keep a lossless source layer and explicit canonical observations. Each adapter publishes:

- **Capability manifest:** provider/product/API version, account and contract scopes, supported dimensions and combinations, interval semantics/timezone, earliest verified date, maximum query range/page size, arrival expectations, revision behavior, coverage exclusions, suppressed fields, monetary denomination, and evidence URI. Distinguish documented from account-observed capabilities and aggregate session counts from live session identifiers/state; daily counts alone cannot support session-continuation modeling. Suppressed activity metrics cannot establish inactivity.
- **Extraction receipt:** immutable run ID, normalized query hash, requested interval, source scope, fetch time, page/manifest list, raw-object checksums, schema fingerprint, parser version, record count, control totals and completion status. Never log credentials. A cursor belongs to its exact query and extraction lineage.
- **Observation:** source-native identity and identity namespace; event/service interval; observation/ingestion times; source-reported currency and decimal value; quantity and unit; charge/usage/estimate classification; charge category; contract/price basis; invoice period; revision/supersession reference; attribution mapping version; and source pointer. Null identity additionally carries a reason such as aggregate, documented-default, unknown or unavailable.
- **Coverage:** source/product/account/interval/dimension partition, expected versus delivered pieces, complete-through evidence, unknown excluded scopes, authorized-scope changes, and status (`complete`, `partial`, `pending`, `unavailable`, `not_applicable`). A successful empty response alone does not establish zero exposure.
- **Financial reconciliation:** source total, normalized total, invoice/control total if available, explained adjustments and residual. Preserve list-valued estimates, contractual effective charges, included-consumption valuation and fixed charges as separate measures. Never silently replace an amount with tokens multiplied by today's public rate.

Use provider-specific update semantics. Replace an aggregate bucket by a new version; activate a full export generation atomically after all manifest chunks validate; ingest genuine adjustment rows as adjustments. Keep prior versions for as-of replay. Do not require a universal request ID where the provider has only aggregated line items. Hashing identical row content is insufficient when legitimate duplicate rows exist: preserve source multiplicity within an import generation.

Represent currency with exact decimal arithmetic and original denomination, including sub-cent values. Convert Anthropic's cents to currency units once; do not apply that conversion to OpenAI's already-currency-valued amounts. Keep billing/pricing currency conversion provenance. Normalize alternate Actual/Amortized or list/effective measures into selectable views, never additive categories. A FOCUS-compatible view may help interoperability, but preserve provider extensions and raw records until its semantics are independently verified.

The ingestion adapter remains read-only. Provider budget/spend-limit mutation endpoints are outside this project's internal-allocation authority even where they share the same Admin API. Backend owns stored financial state and arithmetic; forecasting consumes versioned observations/coverage; Factory interprets company context; frontend displays financial basis and freshness.

## Unvalidated hypotheses and overturning checks

**Hypothesis:** one paired direct-provider feed is the quickest credible forecasting start. Overturn it if account discovery shows most spend in subscriptions/cloud, inaccessible history, weak team mapping or repeated reconciliation residuals. Compare onboarding time and usable complete-day count across candidate sources before selecting.

**Hypothesis:** daily extraction plus overlap refresh suffices for initial horizons. Test on retained source vintages: measure delay distributions and revision magnitude by product/category, including billing close. A fixed refresh window fails if old credits or provider corrections change material targets. Retain scheduled deeper reconciliation and expose its result.

**Hypothesis:** source-provided identity improves team forecasts. Compare attributed coverage and historical mapping stability against simpler company/project series; more IDs can create sparse, misleading series. Establish whether shared gateways and employee moves dominate apparent changes.

No connector was implemented or account-tested in this track. Proposed fault fixtures are in `edges/03-connectors.json`; none are executed results. Remaining discovery includes actual entitlements, real available history, negotiated price basis, tax/credit/seat coverage, and sample reconciliation. These limits are completion criteria for implementation discovery, not reasons to invent an all-in number.
