# Identity, population and financial attribution

The unified architecture needs one stable identity graph, separate exposure and membership histories, and conserved financial partitions. It does not need a bespoke forecast module for every reorganization. Thirteen edge records in `edges/r_identity.json` specify scenarios, defenses, implementation targets and checks. Most are in scope as input semantics and guards, while person-specific numerical quality remains conditional on real roster and attributable usage evidence. A shared key supports shared/account forecasting without establishing any person's adoption history.

## Current behavior and concrete gaps

The existing accounting implementation already defends important cases. `snapshot.py:27–44` provides event-effective and knowledge-dated `Assignment`, Decimal weights and an approved-partition policy distinct from role labels. Selection at lines 173–191 uses event service date and only known assignments, rejects conflicting versions/duplicate recipients/weights above one, retains unmatched weight as `unattributed`, and assigns the final arithmetic residual exactly. Snapshot construction checks company/entity conservation (lines 79–83). Tests already exercise retroactive transfer, partial weights and unmapped identities (`tests/test_snapshot.py:31–52,77–81`). These should be reused.

Three gaps affect implementation priority. First, target `attribution_version` is decorative: its only source occurrence is `contracts.py:116`; selection never binds it to the actual policy. I executed a read-only reproduction using the existing test fixtures: target attribution version `1`, Assignment version `v2`, resulting entity `team:b`, snapshot `ready=True`. A snapshot digest changes, so immutable outputs are not silently overwritten, but the declared target still fails to identify the applied policy. Bind a global immutable allocation-policy snapshot ID/digest, allowing different row revision versions inside it; do not require all Assignment row versions to equal one arbitrary string.

Second, `snapshot.py:193–196` discovers its entity universe from realized rows and fills those entities with zero on every complete source day. That is legitimate accounting arithmetic for a stable covered leaf set. It cannot be reused as a behavioral exposure table: a hire can acquire fictitious pre-entry zeros, never-observed hires disappear, missing seat access looks like disengagement, and pre-existing unknown adoption looks like first trial. `service.py:103–145` likewise builds histories only from daily rows and explicitly rejects an entity first seen in the delayed incurred supplement. Retain accounting behavior but add a separate bitemporal roster/exposure manifest for structural forecasts and named cold-start scenarios. r_adoption independently agrees that employment, access, coverage and engagement must remain separate.

Third, `Assignment.source_entity` matches only `Observation.entity_id` (line 173), across all selected sources. The constructor's error says namespaced identity is required but validates only nonempty strings. Native `user:42` from two providers can collide; one person's two accounts can split a behavioral history. The normalized boundary must either enforce tenant/source/native-ID tuples or carry an explicit verified link registry. Display names and recycled email addresses are insufficient evidence. Direct `team:` leaves are trusted normalized input, so the host must establish that team mapping rather than infer it from provider labels.

## Common mechanisms and top changes

1. Add immutable person/account identity links, exposure spells, and membership records under one revision envelope: tenant, source identity, effective interval, available/known time, evidence and uncertainty. Employment exit gates new work; it does not cancel an ongoing root. Returning contractors preserve confirmed personal prior use while a reused account does not inherit the previous person's behavior.
2. Bind forecasting requests and artifacts to roster, identity and allocation-policy manifests. Historical replays use only facts available at origin; later HR corrections may alter a restated view but cannot change saved old results. Team display renames leave stable IDs intact; splits/merges get explicit effective policies and distinct reporting perspectives.
3. Preserve initiator, executor, beneficiary and payer independently on task/charge records. Choose a stated allocation basis for each returned view. Team memberships and project tags may overlap, but each financial partition plus central/shared/unattributed leaves must equal company cost per date and per predictive path. Team/project cross-tabs are alternative views, never extra amounts.
4. Build cold-start support from known future roster/exposure plus trained cohort priors or explicit scenarios, with no invented prehistory. Unknown subsidiary coverage remains an explicit unobserved pool; aggregate logs cannot identify fictional employees. Cohort priors need empirical evaluation rather than synthetic accuracy claims.
5. Carry current person-level output authority through derived artifacts. Pseudonymous coarse features suffice; prompt content is unnecessary. A caller authorized for team totals must not gain individual identity/history through a roster join. Internal finance reallocations do not alter actual delivered demand or imply provider actions.

## Verification and remaining uncertainty

Required additions are transfer continuity across personal state, provider-ID collision and verified-alias fixtures, rehire/account-reuse spells, new-hire no-pre-entry likelihood, leave versus suppressed-feed distinctions, ongoing work after initiator departure, rename/split/merge conservation, partition-role mismatch and person-scope access checks. Existing conservation tests establish accounting mechanics only. The executed attribution-version reproduction establishes a real contract gap; the new mechanisms above are proposed, not implemented or tested by this contribution. No enterprise roster, private personnel records or attributable real histories were supplied, so neither identity matching accuracy nor individual forecast quality can be inferred. The public token benchmark must label proxy identities as proxies and cannot validate these enterprise mechanisms.
