## Common architecture and top changes

1. Add a small immutable **rating catalog**, separate from the pooled `PricingContract`. A `MeterKey` references identity/spec IDs from capability work and includes seller/channel, billed model revision, meter schema revision, meter name, native unit, tokenizer when relevant, region and service tier. A `MeterQuantity` has that key, nonnegative exact Decimal amount, request/event identity and service instant. Do not retain raw provider totals and billable partitions as independent additive quantities. An explicit schema projection establishes subsets and exclusivity; cache input is either included in gross input or separately counted according to the selected adapter, never both.

2. `RateRevision` carries revision ID, full key, Decimal numerator plus positive denominator, currency, half-open valid interval, `known_at`, evidence reference and rate basis (`list|contract|scenario`). A catalog resolution call requires `as_of` and service time and returns exactly one eligible rule per quantity. Missing/ambiguous rule, absent required dimension or incompatible unit produces a typed error. No latest-rate/default-model fallback. Keep immutable revisions/manifests so a later correction does not rewrite old-origin outputs. Announced future rates can resolve when known before origin; retrieval time does not establish valid time.

3. Retain the existing **complete-pool tariff** below dimensioned rating, with explicit pool ID, reset period and state. Enforce one pool and full period at the public boundary while leaving the existing low-level helper compatible if necessary. Account allowance is consumed after aggregation across all relevant teams; fixed fees are applied once. Distinguish request thresholds from account-period graduated/volume tiers: daily aggregates cannot reconstruct a full-request context threshold. Minimal implementation should support explicit request-local selector quantities with `>`/`>=` declared, or preserve unrateable threshold status when request composition is missing. Do not add a universal multiplier stack; permitted mode/region/cache combinations belong in exact catalog keys or an explicitly validated compatibility rule.

4. Add scenario semantics: `frozen_usage_reprice` keeps immutable meters and only changes compatible rates; `model_migration` references changed tokenizer, cache, reasoning/output, retries and tool-demand assumptions. A rate cut times yesterday's token total is only a mechanical repricing. Model migration/adoption uncertainty should pass through common joint paths, not live in pricing. FX is similarly a typed scenario transform with currency pair, rate convention, date and provenance; until supplied, preserve native currency and reject mixed totals. Tax, invoice settlement, commitment drawdowns, credit expiry and vendor account enforcement remain outside this bounded rating implementation; the financial-target worker owns their amount-layer boundary.

## Verification that changes behavior

Use fixtures around zero, allowance and tier boundaries, including prefix 100/future 1 under retroactive volume pricing; signed `future_increment=-192` must remain valid while physical quantity stays nonnegative. Test price-of-mean against mean-of-path-price with common joint quantities. Dimension fixtures should reject equal numeric amounts with different input/output, tokenizer, region or platform identities. Meter fixtures should accept documented disjoint projections, reject cache subset greater than gross total, and price reasoning included in output exactly once. Unknown breakdown stays unknown, not zero.

Bitemporal tests: announcement known at origin but effective midway through horizon; later correction unavailable at old origin; overlapping eligible rates reject; future-only rate before its valid start rejects. Threshold fixtures just below/at/above the selector boundary must test both rate branch and whether all request units or only excess units reprice. Two requests totaling the same daily tokens may rate differently; aggregate-only input must not claim exact request-threshold cost. Preserve exact rational/Decimal behavior under hostile ambient Decimal precision.

A public-token benchmark can test forecasting **usage**, then separately compute explicitly hypothetical list-price scenarios through this interface. It cannot validate provider billing accuracy, real contract discounts, team ownership or capability equivalence. Never use mixed-model token totals to claim migration savings.
