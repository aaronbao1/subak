# One versioned evidence model for company context

The settled product needs company-context ingestion, not company-context numerology. Internal discussion asks to combine historical spend with current plans (internal transcript line 7, character offsets 1,030–1,500) and communications across the firm. The team describes project timelines informing spend in the mentor discussion (mentor line 43), while the mentor warns that toy backtests miss company complexity (lines 33–39). The master plan resolves scope: source-backed context is core, finance owns internal decisions, numerical forecasting owns numeric effects, and an approved plan does not justify a multiplier (master lines 39, 57–64, 161–173). Both complete transcripts and the entire master were read; this review did not rely on keyword excerpts.

The current implementation already provides most of the right common structure. `src/forecasting/context.py:139` is an append-only in-memory evidence resolver. Immutable document versions and exact Unicode passage ranges defend changed text and misplaced citations. `ContextEvent.known_at` at line 84 takes the maximum of availability, processing, ingestion and review, so an extractor cannot backdate its output merely because an old document existed. Explicit authority-verified supersession is separate from recency; canonical identity deduplicates forwarded copies. Approval, execution state and extraction confidence are distinct. The resolver is `explanation_only`, so a plan or a malicious instruction cannot directly change arithmetic. This is an extraction handoff with caller-supplied verified facts, not evidence of live semantic extraction or a Factory SDK runtime.

Three observations matter for implementation. First, conflict detection is narrower than the modeled state. At `context.py:218–220`, only unequal `value` creates a conflict. A direct reproduction creates two same-scope, same-value events: approved/planned and cancelled/cancelled. Both remain active, but `conflicts == ()`. Thus a consumer looking at the explicit conflict indicator can miss a disputed cancellation. A safe extension needs a small state incompatibility relation, not merely `status != status`: an approved plan and later observed execution can agree, while planned and cancelled execution disagree in an overlapping effective interval without an explicit verified supersession. Preserve both citations and explain the incompatibility; do not infer which source wins.

Second, `resolve` applies supersession before ACL filtering, correctly preventing an old claim from reappearing when its cancellation becomes restricted. But `context.py:221` returns the entire `superseded` ID set without a visibility filter. The reproduction for a principal with no source access returns `events=()`, `superseded=('approved',)`, `restricted_event_count=1`. IDs may encode project names. The result should return only superseded identities whose cited source dependencies are currently accessible, while internally preserving the complete retirement graph and a non-content-bearing restriction signal. This must not resurrect obsolete claims. Restriction counts are an intentional current contract; deciding whether even aggregate counts reveal sensitive information remains a host disclosure policy rather than a mandatory new product feature.

Third, `workload_scenario` at `context.py:245` is precise arithmetic over future quantities, but receives untyped raw values. It documents that callers must supply the unadjusted baseline once, excluding incurred costs and fixed obligations. The reproduction accepts 10→20→40 when the same multiplier is fed the previous output. That is a documented caller boundary, not an unknown bug. The common defense is a baseline reference plus typed quantity/target and an immutable adjustment lineage: bind a scenario to the original forecast artifact and reject repeated application of the same adjustment identity. Do not invent execution probabilities, learned plan effects, or causal savings. `integration.py:161` already records `base_forecast` externally, so the design can elevate an existing convention instead of adding an unrelated module.

The evidence model must also distinguish identity from scope. A canonical assertion deduplicates forwarded evidence; a subject/field/effective interval determines potential incompatibility. Independent research initiatives can both be active without contradicting each other. The extractor must provide an appropriately scoped subject or explicit project/workload scope; broadly mapping every team document to `subject='research', field='plan'` creates false conflicts. The Northstar demo currently uses this broad shape at `integration.py:150`, acceptable for its single research-plan illustration. No automatic project-resolution claim is supported.

Do not add an effective-overlap precondition to all supersession. A verified November replacement can intentionally retire an October plan precisely because it reschedules work. Overlap belongs in contradiction detection; explicit replacement intent governs supersession. Historical as-of origins must still see the October assertion until the replacement becomes known. Likewise, partial textual absence is not measured zero workload, and an approved project is not observed execution. A plan plus observed adoption may describe one occurrence, so future numeric mapping must not sum them as independent impacts.

The finance consumer already implements independent review, atomic internal allocation changes, current authority, stale dependencies and receipts. `FinanceStore._fresh` compares registered material versions and `_evidence_access` checks current ACLs. Its explicit limitation is that trusted host code must enumerate every material dependency; passing no context dependency can omit revocation/staleness protection. A shared evidence reference carrying dependency closure should bridge resolver → immutable context artifact → proposal, preserving the same lineage across all stages. The root should coordinate this with data-contract ownership rather than add a parallel finance authority mechanism.

Priority changes are therefore: state-aware conflict detection with compatible-state tests; ACL-safe supersession metadata; baseline-bound scenario lineage; and reusable dependency closure for context-derived artifacts/proposals. Existing checks should be retained for exact citations, retrospective extraction lags, forwarded duplicates, inert prompt injection, current ACL revocation and explicit scenario assumptions. The attached thirteen edges specify meaningful compound cases, current implementation versus proposal, and verification. These are software invariants and source-grounding guarantees; none establishes enterprise accuracy or a learned narrative cost model.
